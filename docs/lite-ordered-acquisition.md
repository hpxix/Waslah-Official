# Lite: buyer intent → comments → product-ad contacts

This supersedes the earlier listing-only restoration for product-selling Lite searches, regardless of old account source flags.

Haraj runtime is capped at 300,000 ms per 30 requested leads, proportional to quantity (50: 8m20s; 60: 10m; 200: 33m20s). One persisted wall-clock deadline covers automatic passes, recovery, provider queue waits and requests. Only an explicit retry starts a new time allowance; prospect counters and cursors remain intact. For ordered searches, buyer intent receives one quarter of remaining time, comments one third of the time then remaining, and keyword ads the rest. Unused earlier-stage time carries forward. A time-limited stage advances to the next stage without reporting source exhaustion. Requests are cancelled at the deadline; transaction cancellation checks prevent committing interrupted saves. Final database reconciliation may finish after sourcing stops. Enabled Mahally fallback has its own runtime and is outside this Haraj-only cap.

Request pacing now separates starts, preserving the single shared provider lease and configured interval without adding a second interval after a slow response. Local contact work has four bounded workers; actual provider calls still use the shared guard. Progress-only checkpoints coalesce within 500ms, while delivered leads remain durable immediately. Automatic pass continuations have no fixed 250ms delay. The obsolete fixed 100 contact-attempt campaign ceiling is removed; configured provider budgets, denials, Retry-After, consent, ownership, phone validation and deduplication still apply. A runtime allowance is not a promise that the requested number of contacts exists or is authorized.

1. Search direct buying-intent terms and qualify local product + buying-expression evidence.
2. If the target remains short, search actual product aliases and inspect matching product-ad comments. Contact discovery follows the existing verified-authorization, exact profile ownership and Saudi-phone validation path for USER and STORE profiles alike.
3. If still short, search the same actual product terms. A selected keyword in the title **or** body qualifies the ad. No minimum score, buyer-expression, closed/sold, job-seeking, business-description or commercial-word exclusion applies in this stage. A valid Saudi mobile, profile ownership, authorization and deduplication are separate delivery checks; a keyword match alone never fabricates a phone or a confirmed buyer.

The third stage is graded MEDIUM with `demandEvidence:false` and `PRODUCT_AD_CONTACT`; it is not represented as a confirmed buyer. Scope is the actual product vocabulary, not unrelated property/animal/ownership proxies.

For 30 requested leads, process at most 250 buyer-intent listings, then 250 distinct public commenter accounts, then 500 keyword listings. Stop early when the delivered target is reached or a stage has no more sources. Counters persist across continuations; no cyclic reset at the limit. Other target sizes scale proportionally using `ceil(target*1000/30)` prospect units split 25%/25%/50%. Comment seed-listing discovery is additional traversal overhead, separately capped at 250 seed listings per 30 requested leads; it is not falsely reported as processed commenter accounts. All provider request counters include that overhead. A missing/invalid/duplicate/unauthorized phone cannot be delivered and does not extend the prospect allowance.

The ordered policy in `b2c.js` overrides previous source-only account settings for these sales plans. Procurement and legacy non-keyword plans retain their configured source modes. English product aliases, including CCTV, are included in query generation. Existing qualification caches are invalidated by acquisition-policy version. Phone retrieval is guarded by fresh authorization and provider safety controls; the old public-text-only profile no longer silently disables authorized retrieval for ordered runs.

Release prerequisites remain the migrations and trusted verification bridge described in `haraj-consent-workflow.md`. The source tree includes consent changes that cannot be indiscriminately reloaded into the live backend without that coordinated release. An empty authorization registry will not produce authorized saved contacts. No permissions or production consent records are fabricated to achieve a lead count.
