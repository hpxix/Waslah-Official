# Haraj contact automation: implementation package

This is a reviewed design and executable Python reference, **not a production
deployment**. It does not change Wasla permissions or mint production grants.
The current JavaScript authorization/consent implementation remains authoritative
until the new Haraj business-publication path is integrated and deployed.

## 1. Architecture

Approved listing API → metadata-only candidate queue → product keyword matching
→ business-publication evidence OR current verified lookup grant → contact
normalization/ownership → current save decision → workspace deduplication →
encrypted storage → current reveal/download/call decision.

Use the existing Wasla JavaScript provider guard, not independent uncoordinated
Python requests in production. It already coordinates workers, persisted request
budgets, pacing, leases, Retry-After and provider denials. Python illustrates the
same boundaries; `PacedJSON` is a single-worker transport example, not a shared
distributed limiter. Metadata batches use provider-supported cursors. Never infer
an exhausted source from a duplicate page alone, or invent pagination parameters.

## 2. Classification rules

| Evidence | Classification/action |
|---|---|
| Merchant/company identity bound to this exact Haraj author; dedicated, publicly published business telephone/WhatsApp contact field | Public business directory contact |
| Same business identity independently bound to the official company website; number on that site's explicit contact page | Public business directory contact |
| Existing signed authorization covers this workspace, exact subject/number, purpose and action | Authorized contact; permitted actions only |
| STORE status, sales words, commercial-looking ad, comment, public API response, or shared API token alone | Insufficient classification evidence; retain phone-free candidate metadata |
| Conflicting ownership, third-party number in ad/review, number being sold as a product | Exclude; do not identify as the advertiser's business contact |

No Saudi-mobile prefix can distinguish personal from business use. Automated
classification needs provenance, not an LLM confidence score. Where Haraj offers
no documented contact-purpose field, do not invent one. A trusted evidence service
must bind the account to business identity and record source URL, field/DOM path,
observation time, evidence digest and verifier identity. If ownership/business
purpose cannot be established, return `classification_review_required`.

Public-business publication authorizes this product's directory actions
(`save`, `reveal`, `download`) separately from commercial calling. `call` requires
a verified scope. A mobile may be used by a business; a business label alone does
not prove outreach permission.

## 3. Official authorization integration

No official public Haraj consent-signal contract was verified during research.
Do not implement fictitious fields such as `commercial_use_allowed=true`.

The repository already implements these **Wasla endpoints**, not Haraj endpoints:

1. Authenticated client: `POST /lead-agent/contact-consent/requests` with
   `provider: "haraj"`, `author_id`, selected `actions`, and `expires_at`.
   Workspace/user identity comes from the authenticated session, never a body
   supplied workspace ID. The response includes the disclosure and request ID.
2. Trusted verifier: `POST /lead-agent/integrations/contact-consent/requests/:id/challenge`
   using the bridge bearer token. This issues a one-time challenge.
3. Haraj-side/approved first-party flow authenticates the exact subject, verifies
   phone ownership, displays recipient workspace, purpose, scopes and expiry,
   and receives explicit confirmation. OTP alone proves control, not agreement.
4. Only that service posts a signed `grant` event to
   `/lead-agent/integrations/contact-consent/events`. Use `signed_event_headers`
   in `integration.py` to match Wasla's canonical JSON/HMAC protocol.
5. Existing code validates challenge, subject, provider, statement version,
   scopes, expiry, issuer, signature and replay ID before recording the grant.
6. Signed withdrawal or authenticated workspace revoke immediately suppresses
   all subsequent access. Extend the existing revocation transaction to write
   the new Haraj suppression tombstone too.

Internal grant fields already expected by Wasla:

```json
{
  "event_id": "UUID generated by the trusted verifier",
  "issuer": "configured verifier identity",
  "type": "grant",
  "provider": "haraj",
  "request_id": "existing pending request UUID",
  "subject_author_id": "authenticated subject ID",
  "statement_version": "haraj-commercial-contact-v2",
  "verification_method": "haraj_session_and_phone_verification",
  "contact_kind": "personal or public_business",
  "actions": ["lookup", "save", "reveal", "download"],
  "expires_at": "subject-approved expiry, not beyond requested expiry",
  "verified_phones": ["number verified and explicitly approved by subject"],
  "challenge": "one-time challenge issued above"
}
```

This is a contract description, not a receipt to submit with invented values.
Keep signing/bridge credentials solely in the trusted verification service.
Configure the existing `HARAJ_CONSENT_ISSUER`, `HARAJ_CONSENT_SIGNING_SECRET`,
`HARAJ_CONSENT_BRIDGE_TOKEN` and HTTPS `HARAJ_CONSENT_PORTAL_URL` through a secret
manager. A real authenticated portal/verifier must exist before enabling it.

## 4. Database and worker

Apply the existing consent migrations first, then the example `schema.sql` after
review. The additional tables store business evidence, permanent suppression,
encrypted contacts, and phone-free outcomes. Business publication records are
not inserted into the consent registry. Only the evidence-verifier service may
write `haraj_business_publications`; customers and the general collection worker
must not have that privilege. Use separate PostgreSQL roles and grants. Hashes
are pseudonymous identifiers; keep them protected too.

```sh
python3 -m venv /private/tmp/wasla-contact-example-venv
source /private/tmp/wasla-contact-example-venv/bin/activate
pip install 'psycopg[binary]>=3.2,<4'
python3 -m unittest discover -s examples/haraj_contacts -p test_reference.py
# Apply only after reviewing the SQL against your deployment:
# psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f examples/haraj_contacts/schema.sql
```

Call `run_batch` with a psycopg connection configured `autocommit=True`, an
approved source adapter, server-derived workspace ID, target, keyword predicate,
KMS-backed `encrypt` function and cancellation/deadline callback. Do not run
multiple standalone `run_batch` workers for one target; production workers should
use the existing transactional campaign target check in `persistQualifiedB2CLead`.
Existing billing must remain in that same transaction, not in this reference
worker. The Python example does not implement billing.

The source adapter has three explicit methods:

* `metadata_batches`: yield Listing objects; remove phone-like substrings from
  metadata before caching/logging. Persist the cursor after processing a batch.
* `published_business_contacts`: use independently verified evidence, exact
  author binding and dedicated contact fields; do not scan commenter phones.
* `authorized_contacts`: call the approved phone API only after `lookup` passes.
  Preserve author binding from the original listing; reject responses tied to a
  different subject. Use the existing Haraj transport and query contract, rather
  than inventing an endpoint or automatically retrying phone reveals.

Seven executable tests cover Arabic digits, mobile format, business-directory
actions versus calls, denied retrieval, owner mismatch, deduplication, revocation,
phone/action scope, canonical signing and endpoint validation. They are reference
unit tests; the existing Wasla PostgreSQL suite separately covers production
consent locking/expiry/replay and transactional lead saving.

## 5. Integration changes in the actual Wasla backend

1. Keep `contact-discovery.js` pure and classification-neutral. Require matching
   author IDs in both profile and owned-ad responses.
2. Add an evidence-verifier service that records trusted Haraj business
   publications. Account type and keywords never mint evidence.
3. Extend `createContactAuthorizer` in `contact-authorization.js` to check Haraj
   suppression first, then current directory evidence for directory actions,
   otherwise existing verified grants. Use the same subject advisory lock.
4. Extend both signed and workspace revocation paths in `contact-consent.js` to
   create/update Haraj suppression, including when no grant exists yet.
5. Change `saveCandidate` in `b2c.js` so phone-free listing evidence and rejection
   outcomes can be retained without a phone permission. Keep phone-bearing
   save/reveal/export/call gated. This fixes the lost candidate-audit problem.
6. Keep `persistQualifiedB2CLead` as the only production save/bill path. Recheck
   current authorization inside its transaction. Update export/calling paths to
   use the same authorizer; paid reveals never exempt future checks.
7. Canary in an isolated workspace: one verified business publication, one
   opt-in personal contact, one unsupported personal contact, and one revoked
   contact. Assert correct delivery/actions and no duplicate billing.

## 6. Batches, rates, statuses and fallback

Use a durable job per workspace, round-robin the six keywords before fetching
additional pages, and count distinct listings separately from returned entries.
Store every candidate's metadata, match keyword/field, decision and reason;
denied outcomes never contain phone numbers. Use normalized phone hash as a
workspace dedupe key, with author/store identity as an additional key.

Stop on 401/403; honor 429/Retry-After globally, including restarts. Retry only
idempotent metadata reads on bounded transient failures. No token rotation,
proxy substitution, hidden-contact bypass or fake pagination. Keep the existing
five-minute-per-30 Haraj time allowance and truthful partial-result accounting.

Return statuses: `saved`, `duplicate`, `invalid_saudi_mobile`, `missing_phone`,
`ownership_mismatch`, `classification_review_required`, `permission_required`,
`scope_or_phone_not_covered`, `revoked`, `expired`, `rate_limited`, `source_end`.
The reference policy collapses absent/expired grants to `permission_required`;
the production authorizer already returns finer expiry/scope statuses.

If no official authorization integration exists: automatically process verified
public business contacts, retain unsupported candidates without phone data,
and offer an opt-in request through an approved first-party channel. Do not use
an unapproved phone lookup to obtain the number merely to ask for permission.
If business evidence cannot be verified either, keep the public listing URL and
classification reason for review. Report any shortfall rather than pad results.

## 7. Revocation and export

Revocation takes an exclusive lock on the same workspace/subject key used by
collection and export. Write the suppression tombstone, revoke grants and
publication evidence, and invalidate queued call/export work. At reveal,
download or call, read current permission while holding the shared lock; do not
reuse a cached earlier decision. Invalidate application contact caches too.
Files already downloaded cannot be remotely recalled. For long exports, process
small authorized chunks and check each chunk immediately before disclosure.

Reference SQL and Python are not a replacement for the actual provider adapter,
first-party verifier, KMS service, shared scheduler or deployment-specific roles.
Those boundaries are explicit because their contracts cannot be inferred from
an API token or undocumented public responses.
